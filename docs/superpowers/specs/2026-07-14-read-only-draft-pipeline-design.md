# 天猫评论只读草稿流水线设计

## 目标与边界

在现有本地控制台中完成“读取天猫未回复评论 → DeepSeek 分类 → 从活动话术库等概率抽取 → 按当前商品修正 → 保存草稿 → 界面复核”的第一期闭环。

本期始终只读：不定位、填充或点击回复输入框，不调用评价回复接口，不增加任何提交开关。登录与白名单弹窗关闭沿用既有受限驱动。

## 核心流程

1. 启动时复用淘宝登录态，进入“交易 → 评价管理 → 有内容 → 未回复”。
2. 只读取当前页最多 `batchSize` 条评论，提取评论文本、商品标题、订单号、评价时间和页面情感标签。
3. 使用稳定 `sourceKey` 去重；已存在记录不创建第二条。
4. DeepSeek 第一次调用只输出 JSON：`library`、`category`、`confidence`、`reason`、`needsAttention`。
5. 分类必须精确命中当前活动版本；未命中时，好评回落到 `通用整体好评类`，差评回落到 `通用差评类`。
6. 从分类下非空话术等概率抽取一条，并立即保存序号和原文，后续刷新不重新抽取。
7. DeepSeek 第二次调用只做商品名称、产品指代和措辞适配。不得编造规格，不主动提退货退款，不改变模板的客服收口。
8. 保存最终草稿、修改说明和风险状态。淘宝情感标签与 AI 好差评判断冲突、出现高风险承诺或模型明确不确定时标记“需要检查”。

## 组件边界

- `TmallAuthDriver`：登录、进入目标页和读取当前页评论；没有回复写能力。
- `DeepSeekClient`：连接检查、结构化分类、结构化改写；所有返回值在本地严格校验。
- `DraftProcessor`：编排去重、分类回落、随机抽取、风险检查和状态更新。
- `ReplyRepository`：持久化评论及每次处理结果，为仪表盘和结果页提供真实数据。
- Web 结果页：列表、搜索、状态筛选和只读详情；展示评论、商品、分类依据、原始话术、最终草稿与注意事项。

## 数据与幂等

SQLite 新增 `reply_drafts`。`source_key` 唯一；保存评论原文、商品、来源字段、模型判断、模板序号、模板原文、最终草稿、状态、错误和时间。运行中断后，已完成记录不重复处理；失败记录保留原因，后续“重新生成”创建新的处理时间但仍复用同一条评论记录。

草稿按项目现有数据策略默认保留 90 天，并纳入自动清理。活动话术版本变化不改写历史草稿。

## 异常与降级

- 页面结构无法唯一识别：暂停本批次并显示“评论列表需要检查”，不猜测内容。
- DeepSeek 网络或格式错误：该评论记为失败，继续下一条；不生成伪草稿。
- 分类名称无效：按 AI 判断的好/差评库回落通用分类，并在详情中记录回落原因。
- 当前分类无可用话术：该评论失败，不跨库借用话术。
- 商品信息不足：保留模板安全表达，标记“需要检查”，不补写产品参数。
- 暂停按钮：当前 AI 请求结束后停止处理下一条，保留断点。

## 验收

- 模拟天猫页面可稳定提取评论，重复抓取不重复落库。
- 分类精确命中、无效分类回落和差评通用回落均有测试。
- 随机池只包含非空去重话术，每条候选等概率，选中结果会持久化。
- DeepSeek 请求使用 `/chat/completions`、JSON Output、非思考模式，并严格校验 JSON。
- 结果页可查看完整处理证据，但不存在“发送”“提交”“批量回复”等按钮或 API。
- 单元测试、类型检查、构建和浏览器端到端测试全部通过。
