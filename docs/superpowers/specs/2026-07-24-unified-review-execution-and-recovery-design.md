# 天猫评价页面驱动、真实提交与故障隔离统一设计

## 目标

1. 天猫当前页面是本轮可执行评价的唯一来源；SQLite 只用于查看、去重、动作检查点和平台结果回写。
2. 每条评价必须完成“识别、分类、选话术、打开回复框、填写、点击提交、核对平台结果”的完整链路。
3. 单条评价的分类、投诉预审、投诉提交或回复提交失败不得暂停整轮；程序应安全结束当前条并继续下一条。
4. 登录过期、网络波动和页面半加载优先自动恢复；只有验证码或永久性 AI 配置错误才暂停。
5. 产品与话术分类完全依据用户维护的商品名称、分类层级、关键词和话术语义，不在代码中硬编码产品名单。

## 页面驱动与数据库边界

- 自动运行先扫描天猫当前评价页，再按页面快照的 `sourceKey` 查询本地记录。
- 不再启动时领取数据库里的全局 `retry_wait`、`failed` 或其他历史记录。
- 页面没有出现的数据库记录不得触发 AI、浏览器定位、翻页或搜索。
- 页面再次自然出现一条待恢复评价时，才允许定点续接该评价的 AI 或提交检查点。
- 本地状态与平台状态冲突时，先刷新并重新读取平台；最终以平台的回复记录、投诉记录、投诉成立状态或仍可操作状态为准。
- 页面处理成功后，同步把对应本地查看记录更新为成功或平台已处理。

## 旧数据校正

- 对用户已确认平台实际提交成功的旧 `failed` 回复统一校正为 `sent`。
- 删除其余非成功回复草稿及只属于这些草稿的待重试、attempt、动作锁和关联状态。
- 保留成功回复、话术目录、分类、关键词和设置。
- 原数据库只读备份；输出新的独立 SQLite，合并有效 WAL 后执行事务校正和 `integrity_check`。
- 发布包使用校正后的数据库；回复历史最终只展示成功记录。
- 运行时为防重复提交保留最小的 `submission_uncertain` 检查点，但它不作为数据库任务队列。

## 产品、分类和话术智能路由

分类模型必须同时接收商品完整名称、评价正文、情感、所有可用一级分类、二级分类、关键词和话术。

判断顺序：

1. 先根据商品名称与目录语义确定当前商品或产品族。
2. 再根据评价语义选择连接、音质、外观、续航、物流、性价比等具体维度。
3. 优先在当前商品相关的专属分类中选择。
4. 禁止为当前商品选择明显属于另一商品的专属分类。
5. 无法可靠识别专属产品分类时，使用相应情感的通用兜底分类。
6. 关键词是语义证据，不要求逐字命中；未来新增产品只需维护目录，无需改代码。
7. 模型只能返回目录中真实存在的分类。

## 明星评价跳过

- 评价明确涉及明星、艺人、代言人、追星或明星同款等人物营销语义时，不回复、不投诉，直接继续下一条。
- 普通人名或“明星产品”等非人物语义不得误判。

## DeepSeek 单模型

- 分类、情感、产品识别、投诉预审和回复修正统一使用 Pro。
- 设置页只验证和展示 Pro。
- 网络、超时、429 和 5xx 进行有限重试；重试仍失败只结束当前评价并继续下一条。
- 401、403、余额不足或明确模型配置错误属于全局配置错误，停止本轮并给出明确提示。

## 投诉判定与执行

投诉不采用人为抬高门槛的“极端保守”策略：

- 评价内容明确符合平台可投诉类型，事实、类型和投诉描述能够一致对应时，就进入投诉提交。
- 不要求出现额外的严重程度词，也不因措辞不够强烈而拒绝本来符合的平台投诉。
- 普通差评、真实商品体验、质量问题和服务问题不得误投诉。
- 确实无法对应平台投诉类型时，按普通评价进入回复流程。
- 投诉预审临时失败：当前条不回复、不投诉，继续下一条；下一轮再次核验。
- 投诉提交失败或结果不确定：当前条不回复，继续下一条；后续读取平台记录协调结果，禁止重复投诉。
- 页面显示投诉成立、投诉成功、投诉记录或已经没有可用投诉入口时，同步为平台已处理并继续下一条。
- 关闭自动投诉或投诉需要人工查看时，只保留记录并继续队列，不得把整轮升级为 `manual_action_required`。

## 真实回复提交

1. 提交前重新核对目标评价、初评/追评、商品和 `sourceKey`。
2. 打开目标评价的唯一回复框。
3. 找到唯一输入框，填写最终回复并回读确认。
4. 找到唯一提交按钮。
5. 最终点击前写入持久化点击检查点。
6. 调用真实提交按钮的 `click()`。
7. 以页面回复记录、按钮变化或列表状态进行条件等待，不依赖固定等待时间作为成功依据。
8. 平台成功后才写入 `sent`。

点击检查点前失败可安全在后续重试；点击检查点后发生超时、断网或页面关闭时进入 `submission_uncertain`，不得自动重复提交。下一轮读取到平台回复记录后统一协调为 `sent`。

## 页面、网络、登录和店铺恢复

- 删除启动和逐条处理前的独立全局元素健康阻断。
- 正式操作中仍要求目标行、回复框和提交按钮唯一，但暂时找不到时先等待、重读、刷新或重新打开页面。
- 登录过期时自动重新登录，并重新核对当前评价后继续。
- 店铺名称不参与登录、运行、回复或投诉的阻断判断；程序不读取、不保存也不比较店铺名。
- 多次恢复仍无法进入评价页时安全结束本轮，按计划稍后重试，不进入永久人工暂停。
- 验证码或安全验证必须等待人工完成。

## 故障隔离和界面状态

单条分类失败、投诉失败、回复点击前失败、模板暂时无法取得都只结束当前条并继续下一条。界面应准确显示“当前条已跳过，继续下一条”“等待平台确认”或“下一轮重新核验”，不得显示全局“需要人工处理”。

全局暂停仅限：

- 验证码或安全验证；
- API Key 无效、无权限、余额不足等永久性 AI 配置错误。

## 验证与发布

- 单元和集成测试覆盖页面驱动、目录路由、明星跳过、投诉符合即提交、投诉失败继续、真实回复点击、点击后不确定防重、登录恢复和不依赖店铺名。
- 运行服务端、前端和脚本全量测试、类型检查、生产构建和数据库完整性检查。
- 备份数据后，使用真实天猫页面提交两条符合条件的普通评价，核对平台回复记录与本地 `sent` 一致。
- 打包保留校正后的 `data`、话术、设置和必要登录数据，删除日志、测试缓存、临时目录及无关旧包，并验证 ZIP 与数据库哈希。
