# 评价处理范围与人工处理商品设计

## 1. 目标

本次功能把已确认的工作台原型变成真实、可持久化、可执行的产品能力，解决三个问题：

1. 用户可以选择“今天、昨天、近 7 天、近 30 天或自定义日期”，并让天猫抓取和运行控制器真正按该范围处理。
2. 用户可以直接在工作台编辑自动运行时间段与运行间隔，不再跳转到设置页，也不再显示仅供演示的静态数值。
3. 用户可以维护“人工处理商品”名单。名单内商品的中评或差评既不自动回复，也不自动投诉；名单内商品的好评仍正常自动回复。

本设计只改变处理范围、运行计划入口和人工分流策略，不放宽现有的登录、模板、DeepSeek、页面元素、幂等和提交安全门槛。评价回复与投诉仍必须分别通过既有正式流程的全部预检。

## 2. 已确认的产品原则

- “每页 20 条”只是天猫分页大小，不是每轮处理上限。
- 手动运行和自动计划使用同一份评价日期范围。
- 默认日期范围为“近 7 天”，包含今天及此前 6 个自然日。
- 所有日期按 `Asia/Shanghai` 解释，起止日期均包含在内。
- 时间计划支持每天多个不重叠时间段，共用一个 1～120 分钟的运行间隔。
- 关闭自动计划不会删除时间段，用户可以以后重新启用；清空全部时间段则关闭计划。
- 人工处理商品名单是可逆策略，不是永久“已处理”标记。
- 名单中的中评、差评不回复也不投诉；名单中的好评仍自动回复。
- 当平台情感标签为“识别中”或缺失时，只先做情感判断。判为中评或差评则转人工，判为好评才继续完整分类和回复生成。
- 删除名单记录后，仍处于可回复期限且仍在当前日期范围内的历史人工待处理评价可以重新进入自动队列。
- 商品只按天猫商品 ID 精确匹配；缺失或不可信 ID 时安全停止并转人工，标题不参与匹配，禁止静默使用标题或 AI 模糊回退。
- Excel 再导入必须先展示差异，再由用户确认替换 Excel 来源的名单；用户手工添加的记录不能被 Excel 替换误删。

> 后续身份决策（2026-07-16）覆盖本文早期的标题回退和“商品 ID 可选”规则：商品 ID 必填且是唯一权威身份；商品标题可选、只用于展示和搜索，不参与自动匹配或实体合并。

## 3. 范围与非目标

### 3.1 本次实现

- 真实评价日期范围配置、持久化和天猫页面筛选。
- 工作台内真实自动计划编辑器。
- 人工处理商品列表、搜索、手工新增、删除、Excel 预览导入和确认替换。
- 天猫商品 ID 抓取及精确名单匹配。
- 人工分流决策、审计、运行统计和解除名单后的重新处理。
- 针对上述能力的数据库、API、UI、浏览器驱动、单元、集成和端到端测试。

### 3.2 本次不实现

- 不改变好评和差评飞书模板格式。
- 不用 AI 猜测商品是否属于名单。
- 不上传投诉凭证，不勾选旺旺聊天授权。
- 不新增公开的直接回复或直接投诉 API。
- 不把应用改成 Windows 后台服务；自动计划仍只在应用打开时运行。
- 不允许跨午夜时间段；需要覆盖午夜时必须拆为两段。
- 不把原型中的 `localStorage` 数据迁入正式产品。原型仅用于确认交互，正式数据全部由服务端和 SQLite 管理。

## 4. 核心领域模型

### 4.1 评价日期范围 `review_scope`

单例配置：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `preset` | enum | `today`、`yesterday`、`last7`、`last30`、`custom` |
| `custom_start_date` | date/null | 仅 `custom` 必填，格式 `YYYY-MM-DD` |
| `custom_end_date` | date/null | 仅 `custom` 必填，格式 `YYYY-MM-DD` |
| `timezone` | string | 固定 `Asia/Shanghai` |
| `revision` | integer | 每次成功修改递增 |
| `updated_at` | datetime | 最近修改时间 |

校验规则：

- 自定义起止日期必须同时存在。
- 开始日期不得晚于结束日期。
- 自定义跨度最多 90 个自然日，防止误选超大范围导致长时间扫描。
- 非自定义预设不保留旧的自定义起止日期。
- 恢复出厂设置后回到 `last7`。

运行开始时把预设解析为确定的起止日期，并将以下字段冻结到 `automation_runs`：

- `scope_preset`
- `scope_start_date`
- `scope_end_date`
- `scope_revision`
- `scope_timezone`

运行中修改日期只影响下一轮；当前轮继续使用冻结值，避免处理中途改变队列边界。

### 4.2 自动计划

沿用现有 `automation_plan` 与 `schedule_windows`，不创建第二份计划数据。现有合同保持：

- 时区固定 `Asia/Shanghai`。
- 运行间隔 1～120 分钟。
- 每天最多 6 个时间段。
- 时间段开始必须早于结束，且同一天内不得重叠。
- “立即处理一轮”忽略时间段，但仍遵守当前评价日期范围。
- 到达时间段末尾时完成当前单条，之后不再开始下一条。
- 暂停后必须手动继续；停止并关闭计划会在当前单条结束后停机并关闭自动启用。

本次只把编辑入口移动到工作台并复用同一 API。设置页不再保留第二套完整编辑表单，只显示当前摘要和“前往工作台修改”，避免两个入口产生状态误解。

### 4.3 人工处理商品与来源成员关系

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | text | 服务端生成稳定 ID |
| `item_id` | text/null | 天猫商品 ID；新写入必填，null 仅兼容历史数据 |
| `product_title` | text | 可选的用户可读展示标题 |
| `normalized_title` | text | 仅用于列表搜索和展示整理，不参与匹配 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 修改时间 |
| `last_matched_at` | datetime/null | 最近命中时间 |

约束：

- 非空 `item_id` 唯一；所有新增、手工保存和 Excel 导入都必须提供非空商品 ID。
- 历史 `item_id` 为空的记录可以保留供人工整理，但不会自动命中评价；不同商品 ID 允许拥有相同标题。
- 商品标题允许为空；有值时仅更新展示信息，不改变商品身份。
- 相同商品不能因“手工”和“Excel”来源重复创建两个商品实体。

来源不直接存放在商品实体上，而由 `manual_product_memberships` 表表达：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `product_id` | text | 关联 `manual_products.id` |
| `source` | enum | `manual` 或 `excel` |
| `created_at` | datetime | 该来源加入时间 |

`product_id + source` 唯一。同一商品可以同时拥有 `manual` 和 `excel` 两个来源，列表显示两个来源标签。Excel 替换只修改 `excel` 成员关系，绝不删除仍有 `manual` 成员关系的商品。用户在名单页明确点击“移出名单”时，删除该商品的全部来源成员关系；这代表用户主动覆盖当前名单，下一次导入仍包含该商品时，预览会把它列为“新增”。最后一个来源被删除后才删除商品实体。

标题规范化算法版本化为 `manual-product-title-v1`：

1. Unicode NFKC 归一化。
2. 移除零宽字符。
3. 英文字母转小写。
4. 移除 Unicode 空白、标点和符号字符，保留汉字、字母和数字。

标题规范化只服务于列表搜索和展示整理，不做分词、同义词、包含匹配或任何自动身份判断；不同商品 ID 的重复标题允许共存。

匹配矩阵固定如下：

| 评价行 | 名单记录 | 结果 |
| --- | --- | --- |
| 行有可信 `itemId` | 记录有相同 `itemId` | 命中 |
| 行有可信 `itemId` | 记录 ID 不同，即使标题相同 | 不命中 |
| 行没有可信 `itemId` | 任何名单记录 | 身份不可信，安全停止并转人工，不做标题回退 |
| 任何情况 | 只有完整/部分/近似标题或 AI 猜测相同 | 不命中 |

标题永远不参与自动名单命中。评价行缺失商品 ID 时不得猜测或补写身份，应停止自动回复/投诉并保留给人工核对。

新增、手工补充和 Excel 预览统一使用以下身份合并矩阵：

| 输入与既有数据 | 处理 |
| --- | --- |
| 输入有 `itemId`，已存在相同 `itemId` | 复用该实体；非空新标题只更新可选展示信息并写审计 |
| 输入有 `itemId`，不存在相同 ID | 创建该 ID 实体；即使标题与其他 ID 相同也保持独立 |
| 输入没有 `itemId` | 返回“商品 ID 必填”，不能创建、预览通过或按标题合并 |
| 输入的 ID 命中实体，但新标题同时等于另一个不同 ID 实体 | ID 为权威身份，仅更新命中的 ID 实体展示标题；两个 ID 实体继续独立存在 |

评价行没有可信 `itemId` 时结果为“商品身份不确定”：该评价进入人工处理状态且不做回复或投诉，并在高级诊断记录缺失身份，防止自动操作错误商品。

另设单例 `manual_product_catalog_state`，保存全局 `revision` 和 `updated_at`。手工新增、移出名单和 Excel 确认替换都必须在事务中校验调用方的 `expectedRevision`，成功后递增修订号。

### 4.4 人工分流状态

`reply_drafts` 增加：

- `item_id`
- `review_phase`：`initial` 或 `followup`
- `manual_product_id`
- `manual_hold_reason`
- 状态 `manual_product_hold`

`manual_product_hold` 不是终态，不写入“已发送”幂等墓碑。它表示本轮根据当前规则停止自动业务操作。

以下事件可以解除该状态：

- 用户删除命中的手工名单记录。
- 用户确认 Excel 替换后，该商品不再位于 Excel 来源名单。
- 商品 ID 或标题被更正后不再命中。

解除时只把尚未形成外部提交尝试或终态墓碑的评价重置为待发现状态；是否仍未回复、仍在可回复期限且仍在当前日期范围内，由下一次扫描和页面预检重新确认。

### 4.5 与投诉/回复动作锁的互斥

本设计扩展投诉规格中的 `review_action_locks`：`actionKind` 允许 `manual_hold`、`complaint` 或 `reply`，并继续以 `storeId + sourceKey` 唯一约束。

- 人工分流成立时，必须在 `BEGIN IMMEDIATE` 事务中取得 `manual_hold` 锁并写入 `manual_product_hold`；取得失败则停止该评价，不能绕过已有动作锁。
- 回复生成、回复提交、投诉分析和投诉提交的每个内部入口都必须调用统一 `ReviewActionGate`；数据库中为 `manual_hold` 时全部拒绝。
- `manual_product_hold` 不能创建 `reply_attempts`、`complaint_cases` 或 `complaint_attempts`，数据库仓储也必须在同一事务内检查动作锁，不能只依赖控制器调用顺序。
- 进入 `submitting`、`sent`、`submission_uncertain`、活动投诉状态或终态墓碑后，新增人工商品规则不能抢占或改写已有动作锁。
- 尚未提交但已生成的回复草稿，在下一次成为“当前单条”时必须重新经过人工名单门禁；若新规则命中，清空未提交草稿并原子转为 `manual_hold`。
- 移出名单时，只释放仍为 `manual_hold` 且不存在回复/投诉 attempt、活动案件或终态墓碑的锁；其他动作锁保持不变。
- 所有锁转换使用 `lockVersion` 比较并交换，避免名单操作与运行控制器并发覆盖。

## 5. Excel 导入合同

正式服务只接受 `.xlsx`，单文件最大 5 MB，不接受宏工作簿、CSV 或旧 `.xls`。

- 校验 ZIP 文件签名，并限制解压后总大小、单个工作表 XML 大小和单元格数量；超限返回“文件内容过大”，防止小体积压缩包耗尽内存。

解析规则：

- 忽略完全空白的工作表。
- 在非空工作表中寻找表头 `商品ID` 或 `商品 ID`。
- 必须且只能有一个包含该表头的有效工作表。
- 从表头下一行开始读取，忽略空白行。
- 商品 ID 列必须存在且只能有一列，每个数据行的商品 ID 去空后必须非空并按字符串读取。
- 可选识别一列 `商品标题`；标题可为空且仅用于展示。
- 工作簿内重复商品 ID 直接报错；不同商品 ID 的重复标题允许导入。
- 最大 5,000 条，超过后拒绝解析。

导入分为两步：

1. `preview`：解析文件，返回总数、新增、保留、移除、冲突和部分样例，生成 10 分钟有效的一次性 `previewId`；预览同时冻结当前名单 `catalogRevision`。
2. `apply`：用户确认后使用 `previewId` 在单个 SQLite 事务中替换全部 `source=excel` 记录。

确认替换时：

- 手工来源成员关系永不被 Excel 替换删除。
- Excel 新记录若与手工商品相同，则在同一商品实体上增加 `excel` 成员关系并计入“已存在”。
- Excel 中移除的商品只删除其 `excel` 成员关系；仍有 `manual` 成员关系时保留实体。
- 同一事务中解除不再命中的 `manual_product_hold`。
- 事务失败则名单和待处理状态全部回滚。
- 应用时当前 `catalogRevision` 必须等于预览冻结值；否则预览作废并提示“名单已发生变化，请重新预览”，旧预览不得覆盖新修改。

预览内容仅保存在服务进程内存，绑定当前 Web 会话，10 分钟到期且只能使用一次。服务重启后用户需要重新选择文件，不在磁盘保存原始 Excel。

## 6. 天猫页面读取与筛选

### 6.1 固定进入路径

仍按：

`交易 → 评价管理 → 来自买家的评价 → 有内容 → 未回复`

任何筛选器都必须幂等设置：驱动先读取选中状态，仅在状态不正确时点击，不能每轮盲点导致筛选被反向取消。

### 6.2 日期筛选

- `today`、`yesterday`、`last7`、`last30` 优先点击天猫原生快捷项。
- `custom` 使用天猫日期面板选择开始和结束日期。
- 设置后点击“搜索”，再读取页面当前条件或首批结果验证筛选已生效。
- 天猫页面变化导致无法唯一定位日期元素时，进入 `manual_action_required`，禁止继续回复或投诉。

即使页面筛选已成功，服务端仍对每条评价的 `reviewedAt` 进行第二次范围校验。无法解析日期或发现范围外记录时，认为页面状态不可信，停止本轮而不是跳过后继续提交。

### 6.3 行数据扩展

在现有快照基础上读取：

- 商品链接中的 `itemId`
- 完整商品标题
- 评价原文和评价时间
- 主评或追评阶段
- 订单 ID
- 平台情感标签

不改变既有 `sourceKey` 的历史算法，避免旧记录失去幂等关联；`itemId` 作为新增匹配字段持久化。同一 `sourceKey` 再次发现时，只有 `review_phase` 与既有记录一致才允许补充缺失的 `itemId`；阶段不同或两个非空商品 ID 不同都属于身份冲突，必须停止更新。不得改写 `read_only_ready`、`sent` 等既有草稿或终态记录的阶段、回复和审计证据。

## 7. 单条评价决策顺序

每轮执行以下固定顺序：

1. 冻结本轮日期范围和计划版本。
2. 校验登录店铺、页面、日期、有内容和未回复筛选。
3. 读取评价并执行服务端日期范围校验。
4. 按第 4.3 节匹配矩阵匹配人工名单。
5. 未命中名单：进入既有投诉预判、情感分类、模板匹配和回复流程。
6. 命中名单且平台明确为好评：进入正常好评回复流程。
7. 命中名单且平台明确为中评或差评：写入 `manual_product_hold`，不生成回复、不填写回复框、不打开投诉入口。
8. 命中名单且平台标签未知：只调用情感判断；好评继续正常流程，中评或差评转人工。
9. 情感判断失败、输出不合法或语义矛盾：安全转人工并记录失败原因，不做业务操作。

人工名单判定必须发生在投诉入口点击和回复生成之前，确保中差评不会先触发投诉或生成无意义草稿。

### 7.1 实时更新与动态队列

每轮运行冻结日期范围，但不冻结评价列表。天猫未回复队列在运行期间继续变化，控制器必须把它视为动态队列：

- 每次成功完成一个外部动作或人工分流后，重新获取未回复列表并从第一页开始扫描，避免新评价插入顶部后被旧页码跳过。
- 使用稳定 `sourceKey` 和动作锁去重；页码移动、列表延迟更新或新评价插入不能造成重复回复或重复投诉。
- 单次完整扫描会遍历范围内所有分页，不受每页 20 条限制。
- 每次完整扫描未发现新 `sourceKey` 时，再做一次第一页最终检查；检查发现新评价就把空扫描计数归零并继续。
- 连续两次“完整扫描 + 第一页最终检查”都没有观察到新的、可处理的 `sourceKey`，才判定本轮暂时清空。
- 本轮实际读取到的新评价立即处理。发生在最后一次最终检查之后，或因平台分页瞬时重排而本轮从未实际观察到的评价，由下一个自动间隔或下一次“立即处理一轮”发现；产品不承诺消除这个不可避免的页面读取竞态，但绝不把它标记为已处理。
- 自动计划到达时间段末尾、用户暂停或停止时，完成当前单条后结束，不因持续新评价越过控制边界。
- “立即处理一轮”若评价持续进入，会继续处理直到满足双空扫描；用户仍可随时暂停或停止。

原有 785 条分页回归测试扩展加入“处理中从第一页和中间页插入新评价”的场景，必须证明无遗漏、无重复、无回到第一页死循环。

### 7.2 情感判断复用

未知标签时复用已批准的评价分类提示词和结构化输出约束，但使用“仅情感判定”模式：

- 输入评价原文、追评上下文和必要商品信息。
- 输出仅包含 `positive`、`neutral`、`negative`、理由和置信度。
- `不错`、`还行` 等中性表达必须结合完整语境判断；整体偏正面时归好评并使用 `整体好评类`。
- 此阶段不随机抽话术、不改写产品名称、不生成最终回复。

## 8. API 合同

### 8.1 日期范围

- `GET /api/review-scope`
- `PUT /api/review-scope`

`PUT` 接收预设、自定义日期和 `expectedRevision`。服务端只在当前修订号相等时保存；冲突时返回“处理日期已在其他页面修改，请刷新后重试”。响应返回保存后的配置、当前解析出的有效起止日期、修订号和中文摘要。

### 8.2 自动计划

沿用：

- `GET /api/automation-plan`
- `PUT /api/automation-plan`
- `POST /api/automation/start-now`
- `POST /api/automation/pause`
- `POST /api/automation/resume`
- `POST /api/automation/stop`

不新增重复接口。`PUT /api/automation-plan` 增加 `expectedRevision` 并返回新修订号；冲突时拒绝旧页面覆盖。现有中文校验错误继续由服务端生成。

### 8.3 人工处理商品

- `GET /api/manual-products?query=<text>&page=<n>&pageSize=<n>`，响应顶层包含当前 `catalogRevision`
- `POST /api/manual-products`，请求含 `expectedRevision`
- `DELETE /api/manual-products/:id`，请求含 `expectedRevision`，语义为移出全部来源
- `POST /api/manual-products/import/preview`
- `POST /api/manual-products/import/apply`，由预览携带冻结修订号

上传接口使用 multipart，仅接收一个工作簿。列表默认按最近更新时间倒序，搜索同时匹配原始标题和商品 ID。

所有修改写操作审计，但不记录原始 Excel 二进制内容。

`POST /api/manual-products` 同时承担“新增商品”和“按身份合并矩阵为既有同标题无 ID 实体补充商品 ID”的语义；响应必须说明是新建、复用、补充 ID 或合并，便于界面提示和 API 测试断言。

新增、移出名单和确认导入成功后，响应都返回递增后的 `catalogRevision`；前端据此更新缓存。发生修订冲突时前端刷新列表并要求用户重新确认，不能自动重放删除或导入。

## 9. 界面设计

### 9.1 工作台

顶部新增“本轮处理范围”区块：

- 左侧显示范围说明。
- 中间为可点击日期摘要。
- 右侧显示“人工处理商品 · N”，点击进入名单页。

日期摘要打开真实对话框：

- 快捷项：今天、昨天、近 7 天、近 30 天。
- 自定义日期显示双月日历，先选开始、再选结束。
- 未完成范围、开始晚于结束或跨度超过 90 天时禁用确认并显示中文原因。
- 保存期间显示加载状态；保存失败保留当前对话框和用户选择。

自动回复黑色控制卡右侧摘要可点击，打开真实计划编辑器：

- 自动计划开关。
- 多个开始/结束时间段，可新增和删除。
- 共用运行间隔。
- 保存、取消和字段级中文错误。
- 保存成功后工作台状态、当前时段、下一次运行和间隔即时刷新。

### 9.2 人工处理商品页

侧栏新增“人工处理商品”。页面包含：

- 规则说明：仅名单商品的中评/差评转人工，好评仍自动回复。
- 当前总数、手工来源数、Excel 来源数、最近导入时间。
- 搜索框。
- “手工添加”对话框，商品 ID 必填且优先聚焦，商品标题可选且仅用于辨认。
- “导入 Excel”对话框，先选择文件并预览差异，再确认替换。
- 列表显示商品标题、商品 ID、一个或两个来源标签、最近命中和“移出名单”操作。
- 删除前二次确认，明确提示删除后符合条件的评价可能重新进入自动队列。

空状态必须提供“手工添加”和“导入 Excel”两个直接入口。

### 9.3 文案

- 不出现 `CSRF`、`sourceKey`、SQL、HTTP 状态码等开发者术语。
- 不显示固定店铺名称或品牌名。
- 不再出现“自定义日期仅为演示”“计划为示例”等原型文案。
- 保存失败显示用户可行动的中文说明；技术细节只进入默认折叠的高级诊断和脱敏日志。

## 10. 并发、幂等与失败保护

- 同一时间仍只允许一个运行实例。
- 修改日期、名单或计划使用数据库事务、`expectedRevision` 和比较并交换，防止旧页面覆盖新配置。
- 删除名单或确认 Excel 替换与解除待处理状态在同一事务完成。
- 日期范围按整轮冻结；人工商品名单按“每条评价开始”冻结。控制器开始单条前读取 `catalogRevision` 并把修订号和匹配结果写入决策记录，该单条直到结束都沿用此结果。名单修改对正在处理的单条不生效，从下一条评价开始生效；新增与删除遵循同一边界。
- Excel 预览 ID 过期、错会话或重放均返回重新选择文件的中文提示。
- 页面日期筛选、商品行、评价时间或商品 ID/标题状态不确定时停止业务提交。
- `manual_product_hold` 通过 `ReviewActionGate` 和 `review_action_locks` 数据库唯一约束，禁止创建回复/投诉案件和提交尝试。
- 对已经 `sent`、投诉已提交或 `submission_uncertain` 的评价，删除名单不会重新处理。
- 网络或服务重启后，日期范围、计划和名单从 SQLite 恢复；未完成的 Excel 预览作废。

## 11. 数据生命周期

- 日期范围和人工商品名单作为用户设置长期保留，直到用户修改、删除或恢复出厂设置。
- `manual_product_hold` 随评价处理数据保留 90 天。
- 名单变更、导入摘要和自动解除记录作为操作审计保留 180 天。
- 原始 Excel 文件不落盘；内存预览最长 10 分钟。
- 恢复出厂设置清空人工名单、清除预览并把日期恢复为近 7 天；系统凭据仍按现有独立确认流程处理。

## 12. 验收标准

### 12.1 日期范围

- 五种日期选择均可保存，重启后仍存在。
- “近 7 天”严格解析为今天及此前 6 天。
- 自定义范围可以从工作台双月日历完成选择并真实影响天猫筛选。
- 当前运行中修改范围不改变该轮冻结范围，下一轮使用新范围。
- 页面出现范围外或无法解析的评价时停止提交。

### 12.2 自动计划

- 可从工作台打开、修改并保存计划。
- 支持最多 6 个不重叠时间段和 1～120 分钟间隔。
- 保存后摘要、下一次运行和运行状态一致。
- 设置页不存在第二套可产生冲突的计划编辑表单。

### 12.3 人工处理商品

- 可以手工添加、搜索和删除。
- 可以预览用户提供的新版 `中差评剔除产品(1).xlsx`：按“商品标题 + 商品 ID”合同识别当前 4 组商品并忽略空白 Sheet2、Sheet3；商品 ID 从读取、预览到持久化始终按字符串主键处理，不做数值转换。
- 确认导入后名单重启仍存在。
- 再导入能正确展示新增、保留、移除，并只替换 Excel 来源数据。
- 名单商品好评照常回复；中评/差评不回复、不投诉；未知情感先判断再分流。
- 删除商品后，符合日期和平台条件的人工待处理评价可重新进入队列。
- 商品 ID 是唯一匹配依据；标题仅用于展示，缺失 ID 时安全停止且绝不回退标题。

### 12.4 回归与安全

- 785 条、每页 20 条的完整队列测试继续通过，不重复、不回到第一页死循环。
- 不新增公开回复或投诉提交 API。
- Excel 原文件、淘宝密码和 API 密钥不进入数据库、日志或浏览器存储。
- 现有登录恢复、飞书同步、DeepSeek、随机话术、页面元素健康和提交幂等测试继续通过。

## 13. 推荐实施顺序

1. 领域模型、数据库迁移和仓储。
2. 日期范围与人工商品 API，含 Excel 两阶段导入。
3. 天猫读取器扩展、幂等日期筛选和商品 ID 抓取。
4. 处理管线中的人工分流和可逆解除。
5. 工作台真实日期/计划编辑器与人工商品页面。
6. 集成测试、真实只读页面验证和全量回归。

每一阶段先写失败测试，再实现最小代码，通过后再进入下一阶段。正式验收前仍不得用测试数据触发真实评价回复或真实投诉提交。
