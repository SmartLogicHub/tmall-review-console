# 天猫投诉入口与防误投诉修复设计

## 已确认的平台语义

1. 当前评价行没有“投诉评价”或“投诉追评”入口时，表示平台已经处理或判定，本程序无需再次投诉。
2. 有投诉入口时，本程序才可以打开投诉界面、选择平台投诉类型并填写说明。
3. 打开或填写投诉界面不代表投诉成功；点击提交时平台拒绝受理，也不代表本程序投诉成功。
4. 只有本程序点击提交后，页面明确确认提交成功，才能记录为“本程序投诉成功”。
5. “平台已处理”和“本程序投诉成功”必须是不同状态、不同文案和不同审计证据。

## 防误投诉边界

- 普通差评、混合评价、产品质量、降噪、音质、续航、佩戴、价格、物流和服务体验直接进入回复流程。
- 不得因为情感分类为负面就启动投诉预审。
- 只有评论正文中存在明确的平台违规信号，且能够对应受支持的投诉类型时，才调用投诉分析。
- 投诉模型必须给出原文证据、平台投诉类型和一致的投诉描述；任一项不确定或不一致时按普通评价回复。
- 投诉入口不可用、平台拒绝受理、投诉分析临时失败或页面状态不确定时，不进行替代投诉，不暂停整轮，记录具体原因并继续下一条。

## 页面状态证据

- 只读取当前评价行、当前评价阶段、当前可见的操作入口和结果提示。
- 初评不得继承追评的入口或记录，追评也不得继承初评状态。
- 不读取隐藏元素、弹窗外残留元素、其他评价行或整页文本来判断投诉状态。
- 当前行显示“投诉评价/投诉追评”表示可发起投诉，不表示已经投诉。
- 当前行没有投诉入口表示平台已处理或无需投诉，不记录为本程序投诉成功。
- 当前行明确显示投诉提交成功，仅用于平台结果协调；本程序自己的成功还必须存在本次点击提交检查点。

## 数据库边界

- SQLite 用于展示历史、记录本次处理检查点和协调平台结果，不提供脱离当前页面的任务队列。
- 导入的旧成功、失败、待重试或投诉记录不得阻止当前页面上仍可操作的评价。
- 当前页面出现可操作入口时，以刷新后的当前行证据为准；历史数据仅同步更新。
- 打包数据清除旧投诉失败、旧待重试和未完成运行状态，保留成功回复、话术、分类、关键词和设置。

## 故障隔离

- 单条投诉分析、投诉界面、投诉提交或回复处理失败只结束当前条并继续下一条。
- 登录框架刷新、页面暂时脱离或网络波动必须被捕获，重新获取页面/框架后有限重试，不得杀掉后端。
- 启动时把上次异常退出遗留的 `running` 运行记录改为“异常中断”，避免界面永久显示运行中。
- 当前处理状态优先显示，旧投诉失败不得覆盖新的分类重试或回复状态。

## 可见状态文案

- `平台已处理，无需投诉`
- `普通评价，已进入回复流程`
- `投诉条件不足，已进入回复流程`
- `投诉入口暂不可用，本条已跳过并继续`
- `投诉提交未受理，平台已处理`
- `投诉提交成功`
- `页面状态暂不可确认，下轮重新核对`

每条跳过记录还应显示评价阶段、当前行检测到的可见入口/提示、错误代码和时间。

## 验收标准

1. “降噪效果不行，音质及续航可以。”不调用投诉模型，直接分类并生成回复。
2. 任何普通负面商品体验不因负面情感进入投诉。
3. 隐藏或其他行的“投诉评价记录”不能让当前评价跳过。
4. 无投诉入口不写入“本程序投诉成功”。
5. 只有真实点击并确认成功才写入投诉成功。
6. 单条失败后下一条仍被处理。
7. 框架脱离不会导致 Node 后端退出。
8. 回复列表展示当前真实原因，不再统一显示“已按规则跳过”。
