# 投诉自动提交开关设计

## 目标

将当前隐式的投诉自动提交行为改成商家可见、可保存且默认关闭的设置。只有商家主动开启后，已经通过现有 AI 双重核验、事实校验和平台页面校验的投诉，才允许执行现有的平台提交流程。

## 现状与问题

`ComplaintReviewService` 在有 `ComplaintExecutor` 时会从 `prepared` 状态直接执行平台提交。生产入口始终提供该执行器，因此现有版本没有独立的“投诉自动提交”开关。

这会造成界面中“需要人工核对”的提示与实际可自动提交的运行路径难以区分，也无法让商家明确选择是否授权自动投诉。

## 已确认的行为

- 新增 `投诉自动提交` 设置，持久化在现有本地 `settings` 表。
- 新装和升级后的默认值均为关闭：缺少该设置时按 `false` 处理。
- 关闭时：候选投诉仍会完成现有 AI 分析、独立复核、事实校验与描述生成，但不调用平台提交；案件进入 `manual_action_required`，由商家在投诉记录中核对。
- 开启时：仅复用当前已有的安全路径提交，即类型属于固定官方目录、事实校验通过、页面操作验证通过、运行仍未暂停，且仅在最终点击前记录提交检查点。
- AI 超时/契约错误、事实不足、类型不明确、页面变化、暂停、提交结果不确定，始终不再自动尝试提交，保留失败或人工核对状态。
- 自动化运行期间拒绝更改开关，避免一个运行中途改变授权边界；更改只能在下一轮开始前生效。
- 设置页明确标注默认关闭和启用条件；只显示已保存的开关状态，不显示模型内部字段或平台原始响应。

## 平台已处理的例外结果

平台不会一定显示“无需提交”的文字。实际表现是点击投诉提交后，页面没有受理变化，仍停留在同一个投诉弹层；这表示该用户可能已被平台处理，当前评价不能重复投诉。这不是本次提交成功，也不应被当作可重试的失败。

- 浏览器适配器在最终点击后确认：没有成功受理或案件标识，且原投诉弹层仍可见、投诉输入区仍在。只有这组状态同时成立时，报告 `already_handled`。
- 收到该结果后，程序自动关闭唯一可识别的投诉关闭按钮，确认弹层关闭；案件转为现有的 `not_actionable` 终态，删除点击前临时意图、写入防重复处理标记，并立即处理下一条评价。
- 该分支不要求人工确认，也不重复投诉。
- 弹层已变化但未给出稳定受理结果、无法判断是否仍在投诉页、或无法安全关闭弹层时，不使用这个自动跳过分支，沿用现有系统异常保护。

## 架构

`buildApp` 读取设置并把布尔值传给投诉策略工厂。生产入口仅当该值为真时向 `ComplaintReviewService` 传入 `ComplaintExecutor`；否则不传入执行器，服务按既有无执行器逻辑将已准备的投诉转为人工核对。浏览器投诉流会在提交后检查投诉弹层是否未发生变化；满足该条件时关闭弹层，并把结果通过执行器、安全状态机和案件仓库写为不可重复的终态。

设置 API 在读取时返回 `complaintAutoSubmit`，在写入时仅接受布尔值。设置页使用受现有会话与 CSRF 保护的 API 保存开关，保存成功后刷新设置缓存。

## 验收标准

1. 全新数据库的设置 API 返回 `complaintAutoSubmit: false`。
2. 空闲时可以把该值保存为 `true` 或 `false`；运行中写入返回冲突错误，不改变已生效的运行边界。
3. 关闭开关时，生产投诉策略没有执行器，合格候选进入人工核对而不发生平台提交。
4. 开启开关时，生产投诉策略保留现有提交检查点、去重和结果不确定保护。
5. 点击后仍停留在原投诉弹层时，程序关闭弹层，案件成为 `not_actionable` 且不再重试或要求人工确认；不明确的页面状态不允许走这条分支。
6. 设置页显示默认关闭状态、风险说明与保存结果；不因旧错误而显示错误的成功状态。
