# 投诉与好差评多轮裁决设计

## 目标

自动回复必须对每条可处理评价给出可靠的最终动作，重点防止把差评当成好评，同时避免误投诉。模型判断发生冲突时由第三次裁决得出最终结果，不把判断责任交给用户，也不因为语义冲突直接跳过普通评价。

## 固定业务规则

- 人工处理商品名单只按商品 ID 精确匹配，商品标题只用于展示。
- 名单商品的中评、差评直接跳过，不回复、不投诉。
- 名单商品的好评继续正常自动回复。
- 名单商品缺少可靠情感结果时，必须先完成下述情感分类与冲突裁决；在得到最终好评或差评前不得进入投诉流程。中评按差评侧处理。
- 名单规则产生的是程序内部拦截状态，不创建需要用户判断的人工队列。
- 投诉判断先于普通回复生成；确定无需投诉后才进入好差评分类和话术选择。

## 投诉判断

### 第一轮：资格分析

第一轮只允许从固定的 13 个官方投诉类型中选择，并输出严格结构化结果：是否为投诉候选、官方类型、事实码、评价原文 Unicode 引用区间、置信度和简短理由。

程序必须校验类型与事实码的固定映射、引用区间确实位于评价原文、引用非空，以及该投诉类型要求的现有客观事实。模型不得创造订单、物流、图片、聊天或竞品事实。

### 第二轮：独立审查

只有第一轮认为需要投诉时才调用第二轮。第二轮使用独立的审查系统提示词，只接收评价原文、允许的官方类型和当前可核验事实，不接收第一轮理由或对话历史。

若两轮都判定为投诉候选，且官方类型、事实码和引用区间一致，再进入程序硬校验。通过后允许提交投诉。

### 第三轮：冲突裁决

两轮的决定、类型、事实码或引用区间不一致时，调用第三套裁决提示词。裁决器接收评价原文、可核验事实以及两份结构化结论，但不接收模型思维过程，必须输出一份新的严格结构化结论。

第三轮判定投诉时，必须与前两轮中的至少一轮在官方类型、事实码和引用区间上完全一致，并再次通过程序硬校验，才允许提交。任何类型缺少所需客观事实时，最终结论固定为“不投诉”，继续进入好差评判断，而不是跳过或交给用户。

## 好差评判断

### 第一轮：正常分类

沿用现有分类、话术库和产品信息修正流程。第一轮必须输出好评或差评、置信度和简短理由。

### 第二轮：风险触发复核

明确、无负面信号且置信度不低于 `0.90` 的好评不重复调用模型。风险信号由确定性文本规则与模型置信度共同触发；以下任一情况触发独立负面复核：

- 转折或前后态度变化；
- 后悔、无奈或勉强接受；
- 价格或价值否定；
- 明确质量、物流、服务或使用问题；
- 反讽、阴阳表达或表面称赞；
- 第一轮置信度不足。

第二轮使用独立复核提示词，不接收第一轮理由。两轮一致为好评时进入好评话术流程；第二轮判为差评时构成冲突，必须进入第三轮裁决，不直接采用任意一轮。

### 第三轮：最终情感裁决

两轮情感结果冲突时调用第三套裁决提示词。第三轮必须输出最终好评或差评，不返回“未知”或“转人工”。裁决仍存在混合或模糊负面信号时，按差评处理，优先防止差评被错误发送好评话术。

## 数据流与优先级

1. 读取评价和商品 ID，确认日期范围及评价阶段。
2. 应用人工处理商品名单规则；名单商品先取得最终情感结果，最终为中评或差评时立即安全跳过且不得进入投诉流程，最终为好评时继续正常流程。
3. 对其余评价执行投诉第一轮；候选才执行第二轮，冲突才执行第三轮。
4. 只有通过投诉硬校验才填写并提交投诉；否则进入情感分类。
5. 情感第一轮判定为存在风险的好评时执行第二轮，冲突时执行第三轮。
6. 根据最终好评或差评选择对应话术，提交前重新核对 sourceKey、商品和评价阶段。
7. 已提交投诉的评价不得回复；已提交回复的评价不得投诉或重复回复。

## 错误处理

- 模型格式错误、网络错误和超时沿用现有有界重试，不把技术故障当作语义冲突。
- 有界重试全部失败时停止当前自动运行并显示错误，不猜测投诉或情感结果。
- 浏览器提交结果不确定时保持现有防重复锁，不再次点击。
- 第三轮裁决只解决有效模型结果之间的语义冲突，不绕过程序硬校验。

## 测试与验收

- 证明投诉第二轮使用不同系统提示词，且没有收到第一轮理由。
- 覆盖投诉两轮一致、决定冲突、类型冲突、事实码冲突、引用冲突和缺少客观事实。
- 证明第三轮投诉结论仍须经过固定类型、事实码、原文引用和客观事实校验。
- 覆盖明确好评不复核、转折好评触发复核、二轮判差评、二轮冲突进入三轮、模糊裁决最终按差评。
- 覆盖名单商品中差评不回复不投诉、名单商品好评正常回复。
- 全部服务端、领域层、前端和端到端测试通过，类型检查和生产构建通过。
- 关闭旧实例后重新生成不包含本地凭据和数据库状态的 Windows 便携版，并从新 EXE 完成启动、单实例、配置页、队列和安全停止冒烟验证。
