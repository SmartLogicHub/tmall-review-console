# 页面识别驱动、旧数据校正与话术目录智能路由设计

## 背景与故障边界

Windows 包允许用户把旧 `data` 数据库导入新版本以查看历史记录。当前自动化启动后会先从数据库领取 `retry_wait` 记录，再扫描天猫页面。这样会把仅用于展示的导入记录当成执行队列：程序生成回复后才尝试在当前页定位评价，定位不到时记录失败并继续下一条。

正确边界是：天猫当前页面是本轮可执行评价的唯一来源；SQLite 只保存历史、处理检查点和展示状态。数据库中存在一条记录，不代表本轮有权对它执行回复。

同时，好评和差评话术表由用户持续维护。产品识别不能在代码中写死“扩音器”等名称，而要依据商品名称、评价语义、话术分类名称和分类关键词动态选择。

## 目标

1. 每轮只能处理本轮从天猫页面实际识别到的评价。
2. 页面自然再次识别到一条 `retry_wait` 评价时，才允许续接其 AI 检查点并提交；不得为了数据库旧任务专门翻页或搜索。
3. 导入数据库中未被页面识别到的记录只能展示，不能阻塞、触发或抢占自动回复。
4. 对用户已经确认平台实际提交成功的旧数据，将 `failed` 记录一致地校正为成功，并删除其余非成功记录，最终只保留成功回复。
5. 根据用户维护的话术目录动态识别产品专属分类；未来增加其他产品时无需修改代码中的产品名单。

## 非目标

- 不自动推断任意失败记录是否真的提交成功；旧数据校正仅针对用户本次明确指定的数据库副本。
- 不覆盖或直接修改用户提供的原始数据库文件。
- 不新增产品名称、别称或品牌的硬编码词典。
- 不为了恢复数据库旧任务主动遍历天猫历史页面。

## 方案比较

### 方案一：保留数据库优先重试，并在提交前专门寻找目标

能够续接旧任务，但会让导入数据继续驱动浏览器行为，与“页面识别才处理”的要求冲突。拒绝采用。

### 方案二：给导入数据增加只读标记

可以隔离导入记录，但需要新增导入来源元数据、迁移和 UI 概念；普通复制 `data` 的场景也无法可靠判断来源。复杂度高且不必要。拒绝采用。

### 方案三：页面扫描作为唯一调度器，数据库只提供已识别记录的状态

删除自动化启动时的全局数据库重试队列。页面扫描得到快照后，再按 `sourceKey` 查看数据库状态：新评价正常处理；页面重新出现的 `retry_wait` 评价定点领取并续接；已发送或不可操作记录跳过；数据库中没有出现在本轮页面快照中的记录完全不参与执行。采用该方案。

## 自动回复数据流

1. 自动化完成登录和页面验证。
2. 先读取天猫当前未回复列表，取得本轮真实页面快照和目标行提示。
3. 对每个页面快照按 `sourceKey` 查询本地记录：
   - 不存在：创建草稿，执行分类、选话术、生成回复并提交。
   - `retry_wait`：只领取当前快照对应的这一条记录，续接已有 AI 检查点，然后使用本次扫描建立的目标行提示提交。
   - `read_only_ready` / `needs_attention`：按现有安全规则提交。
   - `sent` / `not_actionable` / `manual_product_hold` / `submitting` / `submission_uncertain`：保持现有防重复策略并跳过。
   - `failed`：保持终态，不自动重新执行，除非现有人工重处理入口明确触发。
4. 页面扫描未返回的本地记录不进入任何处理队列，也不影响本轮范围检查。
5. 同一轮仍使用 `seen` 集合防止重复处理；下一轮页面再次出现时再根据当时页面状态决定。

## 页面观察型 AI 重试

新增一个“领取当前已观察重试”的原子仓储操作。它必须同时验证：

- 指定草稿仍为 `retry_wait`；
- `sourceKey` 与当前页面快照一致；
- 没有投诉、回复或其他动作锁冲突；
- 没有其他处理租约持有者。

该操作只领取调用方明确指定的记录，不能像现有全局重试领取一样返回数据库中的其他记录。领取成功后沿用现有 `processClaimedRetry` 检查点恢复逻辑。领取失败则安全跳过当前快照，不得回退为全库搜索。

自动计划保留既有 `next_retry_at` 退避；手动“立即处理一轮”沿用现有允许提前重试的语义。无论是否到期，都必须先有当前页面快照。

## 话术目录驱动的智能产品识别

分类模型继续接收：

- 当前商品完整名称 `product`；
- 当前评价正文 `review`；
- 页面情感标签；
- 好评和差评目录中的 `primaryCategory`、`category`、`keywords`。

分类规则增加产品相关性优先级：

1. 先从分类名称和关键词语义中判断哪些分类属于当前商品或商品类型。
2. 商品名称与某组产品专属分类在名称或语义上相关时，优先在该产品组内选择。
3. 再依据评价语义选择音质、外观、续航、连接、物流、性价比或通用类等具体维度。
4. 不得为当前商品选择明显属于另一产品的专属分类。
5. 当前目录没有可确认的产品专属分类时，才使用相应好评或差评通用分类。
6. 关键词是语义证据，不要求逐字精确匹配；商品别称或未来新增产品由模型结合用户维护的目录动态判断。

代码不包含“扩音器”“小蜜蜂”等固定产品名单。扩音器只是回归样例；测试还必须使用另一个虚构产品目录证明规则可泛化。

## 旧数据库校正

校正工具对本次指定的数据库副本执行，原文件保留不动。执行前复制主库并合并有效 WAL，运行 `PRAGMA integrity_check`，然后在单一事务中完成：

### `failed` 记录

- 仅校正用户已确认平台实际提交成功、当前草稿状态为 `failed` 的回复记录。
- 草稿改为 `sent`，清除草稿错误码和错误信息。
- 对应失败 attempt 改为 `sent`，清除错误字段，写入“旧数据经用户确认平台已提交”的证据。
- 补齐 `submitted_at`、`verified_at` 和更新时间；时间优先使用已有 attempt 更新时间，无法取得时使用校正时间。
- 释放回复动作锁，并按现有仓储约束建立 `reply_sent` 防重复记录。

### 其余非成功记录

- 删除 `retry_wait`、`discovered`、`not_actionable` 及其他未转换为 `sent` 的草稿，以及仅属于这些草稿的 AI 调用、attempt、动作锁和关联状态。
- 使用现有操作员记录清理边界或等价的外键安全事务，不能留下孤儿记录。
- 已有 `sent` 记录和由 `failed` 校正得到的 `sent` 记录保留；校正输出中的回复草稿最终只能存在 `sent` 状态。

校正完成后再次执行完整性检查，并输出各状态变更前后的计数。交付物是一个新的、可复制进包内 `data` 目录的干净 SQLite 文件，不携带 WAL/SHM。

## 错误处理

- 页面扫描失败时停止或进入现有人工处理状态，不允许回退到数据库旧任务。
- 当前快照对应的重试领取发生锁冲突时只跳过该条，不处理其他数据库记录。
- 分类模型返回其他产品分类时按模型合同失败重试；不得静默使用错误产品话术。
- 旧数据校正的任一步骤失败时回滚整个事务，原始文件和输出前备份保持不变。

## 测试与验收

### 页面识别驱动

- 数据库存在 `retry_wait`，但页面返回空列表：不得调用 AI、不得提交、不得改变该记录。
- 数据库存在多个旧 `retry_wait`，页面只返回其中一条：只续接这一条。
- 页面返回一条新评价：正常生成并进入真实提交链路。
- 页面返回一条 `retry_wait`：使用本轮目标行提示续接并提交。
- 导入记录不在当前日期范围或当前页面时，不阻塞整轮。

### 智能产品分类

- 商品为扩音器且目录包含扩音器专属分类时，模型输入完整包含商品、分类和关键词，并要求优先扩音器分类。
- 商品别称未逐字包含“扩音器”时，规则仍允许根据目录语义匹配扩音器分类。
- 使用另一个未来产品及其专属分类重复测试，证明没有硬编码扩音器。
- 当前商品没有专属分类时仍能选择通用分类。
- 模型选择明显属于其他产品的分类时触发模型合同重试或安全失败。

### 旧数据校正

- 所有目标 `failed` 草稿和 attempt 一致变为 `sent`，没有残留错误和动作锁。
- 所有未转换为 `sent` 的回复草稿及其从属记录被删除，没有孤儿记录。
- 输出数据库中的回复草稿状态只有 `sent`。
- `PRAGMA integrity_check` 返回 `ok`，输出数据库可在无 WAL/SHM 的情况下独立打开。
