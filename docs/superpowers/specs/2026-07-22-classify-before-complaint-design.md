# 先分类、后投诉核验设计

## 问题

真实 Windows 包运行时，天猫评价列表中的 61 条记录都没有稳定的页面情感标记，因此以 `sentimentLabel: "unknown"` 进入系统。现有生产投诉策略把 `unknown` 无条件视为投诉候选，而且投诉预审发生在普通好差评分类之前。结果是 61 条普通评价全部先进入投诉模型，并在投诉模型抛出通用错误后停留于 `discovered`，表现为“待分类 / 投诉预审内部失败”。

## 目标行为

处理顺序调整为：

1. 采集并持久化评价；
2. 执行自动跳过商品策略；
3. 使用普通评论分类与情感复核得到最终 `good` 或 `bad` 语义；
4. 用最终语义与明确违规信号筛选投诉候选；
5. 只有负面评价或包含明确违规信号的评价进入严格投诉核验；
6. 投诉成立时停止回复并保持投诉动作锁；
7. 投诉不成立时选择话术、生成回复并保持回复动作锁。

页面 `unknown` 只表示 DOM 未提供可信情感元数据，不再直接代表投诉风险。

## 历史失败恢复

仅允许以下历史投诉预审记录进入恢复路径：

- 回复仍为未提交的 `discovered`；
- 投诉状态为 `failed` 或尚未分析完成的 `discovered`；
- 没有投诉类型、事实码、投诉描述；
- 没有任何投诉提交 attempt；
- 当前投诉动作锁版本与案件一致。

恢复时允许普通分类持有短期 AI 处理租约。分类完成后：普通评价把未启动的投诉分析原子释放为 `no_complaint` 并把动作锁转为 `reply`；真实投诉候选继续沿用原投诉锁进行严格复核。已选择投诉类型、已准备、已点击、已提交或结果不确定的记录绝不释放。

## 错误处理

- 普通分类失败：沿用现有分类重试和熔断，不创建新的投诉案件。
- 投诉核验失败：保持投诉锁，界面显示具体投诉错误类型，不继续生成回复。
- 暂停或停止：AI 请求边界继续检查租约与 `shouldContinue`，不在停止后启动下一阶段。
- 动作锁冲突：立即安全跳过，禁止同一评价同时生成回复和投诉。

## 验证

- 回归测试必须复现 `unknown` 普通好评在旧逻辑中先调用投诉模型并失败的行为。
- 新逻辑必须证明普通分类调用早于投诉筛选。
- `unknown` 最终好评不得调用投诉模型；最终差评必须调用投诉核验。
- 61 条同类历史 `internal` 失败必须能在下一轮安全释放并完成回复生成。
- 已有投诉提交意图或 attempt 的记录必须保持不可释放。
- 完整 server/web/domain 测试、类型检查、构建和 Windows 打包必须通过。
- 新 EXE 必须在真实 Chromium 中验证控制界面，并在不提交真实回复或投诉的安全范围内复测状态流。
