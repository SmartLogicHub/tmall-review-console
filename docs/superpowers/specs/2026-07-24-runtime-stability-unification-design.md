# 天猫回复与 DeepSeek 运行稳定性统一修复设计

## 目标

自动回复只以当前天猫评价页面为执行依据。页面暂时未加载完整、网络波动或提交后连接中断时，系统不得把已经提交的回复误记为失败，也不得因为重复的全局元素验证阻断处理。DeepSeek 统一使用一个模型，减少双模型可用性依赖。

## 已确认根因

1. 独立的关键元素验证会在启动和发现新评价时重复检查评论列表、回复入口、回复框与提交按钮。天猫局部刷新或网络较慢时，这些元素可能暂时缺失，从而被误判为“界面不可信”。
2. 另一台电脑的数据库出现大量 `TMALL_BROWSER_OPERATION_ABORTED`，随后又出现“目标评价已不在未回复列表中”。这与“平台已接收回复、但本地未获得稳定页面结果”一致。
3. DeepSeek 连接测试并发调用 Flash 和 Pro，任一模型单次 5xx 即判定整体验证失败。实际分类、情感判断和投诉分析依赖 Flash，因此 Flash 波动会让评价进入等待重试，即使 Pro 正常。

## 方案

### 1. 去掉独立元素验证阻断

- 淘宝登录和进入评价管理页只验证登录状态、店铺身份和评价页面可访问。
- 不再以持久化的“元素健康状态”作为自动回复启动条件。
- 不再在发现每条新评价前打开回复框做全局元素预检。
- 每条正式回复仍在点击前核对目标评价唯一标识、评价阶段、商品、店铺、唯一回复框和唯一提交按钮。

### 2. 页面暂时不稳定时重读

- 将 `TmallReviewPageStateError` 和 `ReviewFilterStateError` 视为可能由页面半加载产生的瞬时读取错误。
- 等待页面稳定后重新读取，最多进行有限次数重试。
- 只有连续重读仍无法确认时才暂停，并保留具体原因；不创建“处理失败”的评价记录。

### 3. 提交结果按点击边界处理

- 提交按钮点击边界前失败：未提交，可安全跳过当前读取并在后续页面扫描重新识别。
- 已进入提交点击边界后出现超时、断网或页面关闭：记录为 `submission_uncertain`，禁止重复提交。
- 下一轮从天猫页面读取到“评价回复记录/追评回复记录”时，把对应本地记录和尝试统一更新为 `sent`。
- “目标已不在未回复列表”不得直接证明失败；没有平台回复记录时保持不确定，不自动重发。

### 4. DeepSeek 统一使用 Pro

- 分类、情感判断、复核、投诉分析、话术商品修正全部使用 `deepseek-v4-pro`。
- 设置页只显示和验证一个模型。
- 连接测试对 5xx、429、超时和网络错误进行有限重试；瞬时波动不判定 API Key 无效。
- 401/403、余额不足和明确的模型配置错误仍立即报告。
- 运行时 AI 瞬时失败保留现有安全重试与等待机制，不提交未经生成和校验的回复。

## 数据与界面

- 数据库仍作为查看、去重和页面结果回写记录，不作为启动时待处理队列。
- 历史 `sent` 数据和现有话术、设置、浏览器登录状态在新包中保留。
- 运行中心不再展示页面元素健康拦截；设置页 DeepSeek 卡片展示单一 Pro 验证结果。

## 验证

- 单元测试覆盖：无元素预检阻断、页面重读恢复、点击后异常进入不确定、平台回复记录回写成功、单一 Pro 模型使用、连接测试瞬时重试。
- 运行服务端、前端、领域层和打包脚本完整测试。
- 执行类型检查与生产构建。
- 使用包含现有数据的发布目录冷启动，核对数据库完整性、API 状态、话术数量和 DeepSeek 单模型展示。
